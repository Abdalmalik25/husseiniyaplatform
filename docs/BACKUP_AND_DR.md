# النسخ الاحتياطي المشفّر والتعافي من الكوارث — ALHUSAINIA

## نظرة عامة

نظام نسخ احتياطي مشفّر وقابل للتحقق مدمج في المنصة:

| الخاصية          | التنفيذ                                                                                                              |
| ---------------- | -------------------------------------------------------------------------------------------------------------------- |
| التشفير          | AES-256-GCM مع اشتقاق المفتاح scrypt (N=2^14) وملح عشوائي لكل نسخة                                                   |
| سلامة البيانات   | SHA-256 لكامل الملف + بصمة المفتاح في الـ Manifest — أي عبث أو تلف يُكتشف قبل الاستعادة                              |
| تنسيق الملف      | `ALSBK1` : MAGIC \| salt(16) \| iv(12) \| authTag(16) \| ciphertext                                                  |
| التخزين          | S3 عبر Forge (أساسي في الإنتاج) + نسخة محلية `.backups/` (تطوير/استضافة ذاتية)                                       |
| الاستبعاد الأمني | جداول `users` و`loginAttempts` و`apiKeys` و`biometricTemplates` لا تُصدَّر أبداً — تسريب نسخة لا يسرّب بيانات اعتماد |
| الصمود           | كل خطوة خارجية ملفوفة بـ retry/timeout (`server/_core/resilience.ts`)، والفشل لا يُسقط الكرون أبداً                  |

## متغيرات البيئة

| المتغير                 | إلزامي؟            | الوصف                                                                                                            |
| ----------------------- | ------------------ | ---------------------------------------------------------------------------------------------------------------- |
| `BACKUP_ENCRYPTION_KEY` | **نعم في الإنتاج** | سر رئيسي ≥ 16 حرفاً. بدونه النسخ **معطَّل تماماً** (fail closed). في التطوير يُستخدم مفتاح dev غير آمن مع تحذير. |
| `BACKUP_DIR`            | لا                 | مجلد النسخ المحلية (افتراضي `.backups`).                                                                         |

> ⚠️ فقدان `BACKUP_ENCRYPTION_KEY` = استحالة فك تشفير النسخ. خزّنه في مدير أسرار واحتفظ بنسخة خارجية موثقة.

## التشغيل الآلي

- **كرون ليلي**: نداء `/api/cron/tick` الساعي يشغّل نسخة كاملة مرة واحدة يومياً (`runNightlyBackupIfDue`) — لا يتكرر خلال اليوم ولا يُفشل النداء عند تعطله.
- **الاحتفاظ**: آخر 30 نسخة في الفهرس؛ النسخ المحلية الأقدم تُحذف تلقائياً.

## نقاط tRPC (للمدراء فقط — adminProcedure)

```ts
trpc.backup.run.mutate({ tenantId: null }); // نسخة كاملة الآن
trpc.backup.list.query(); // الفهرس (بدون مسارات الملفات)
trpc.backup.verify.mutate({ id }); // تحقق سلامة بدون كتابة
trpc.backup.restore.mutate({ id, dryRun: true }); // الافتراضي: تدريب فقط
trpc.backup.restore.mutate({ id, dryRun: false, confirm: true }); // استعادة حقيقية
```

الاستعادة الحقيقية **إضافية لا تدمّرية**: تُدخل الصفوف مع تخطي التعارضات — الحذف الجذري قرار DBA صريح خارج التطبيق.

## إجراء التعافي من كارثة (RTO ≤ ساعة / RPO ≤ 24 ساعة)

1. جهّز قاعدة Neon جديدة وشغّل الهجرات (`pnpm db:migrate`).
2. اختر النسخة من `trpc.backup.list` ثم تحقق منها (`verify`) — يجب أن يعيد `ok: true`.
3. شغّل `restore` بـ `dryRun: false, confirm: true` من حساب مدير.
4. راجع عينات مالية (ميزان مراجعة + رصيد عميل) قبل فتح النظام للمستخدمين.
